出力形式: 仕分け表 → 削除候補の確認リスト → 要改修Skillの改訂案（1つずつ）


■ ③諦めた自動化への再挑戦

昔挑戦して諦めた自動化に、いまのあなたの能力で再挑戦してほしい。

自動化したいこと: 【例: 毎朝、業界ニュースを集めて要約をSlackに投稿する】
前回諦めた理由: 【例: 記事の取得が不安定で、要約の品質もばらついた】

進め方（必ずこの順で）:
1. 全体設計: 処理の流れ・必要なツール・失敗しやすい箇所を先に示す
2. 最小構成: まず一番小さく動く形を作る（機能は最低限でいい）
3. 動作確認: 実際に動かして結果を見せる。動かない場合は原因の切り分けから
4. 拡張: 動いてから機能を足す。1つ足すごとに動作確認

守ること:
- 一発で完成形を目指さない。「動く最小構成」を最優先
- 認証情報・APIキーはファイルに直書きしない
- 完成したら、使い方と失敗時の対処をREADMEに残す


■ ④自分用アプリの積年バグ退治

あなたはこのプロジェクトのバグハンターです。

対象: 【リポジトリ / フォルダのパス】

やること:
1. コードベース全体を調べ、「前から直っていない不具合・怪しい箇所」を洗い出す
   - 放置されたTODO/FIXME、握りつぶされているエラー、再現条件不明のまま止まっている問題も対象
2. 見つけた問題を「再現手順・影響・原因の仮説」つきで重要度順に一覧化する
3. 私が選んだ問題から修正に入る。修正前に方針を出して承認を待つこと
4. 修正したら必ず実際に動かして検証する。「たぶん直った」で報告しない

出力形式: 問題一覧（重要度順） → 私の選択待ち → 修正方針 → 修正 → 検証結果


■ ⑤メモリのブートストラップ（教訓の移植）

あなたのメモリを「私専用」に育て直します。

やること:
1. これまでのセッション履歴を振り返り、次の2種類を抽出する
   - 私から受けた修正・注意（同じ指摘を2回以上受けたものは最優先）
   - うまくいった進め方・私が好む出力の型
2. 抽出した教訓をメモリに保存する。ルール:
   - 1ファイル1件、冒頭に1行要約
   - 「なぜそうするのか」の理由も書く
   - すでにある教訓と重複したら、新規作成せず既存を更新する
3. あわせて既存メモリを点検し、間違っているもの・古くなったものは削除または修正する

最後に: 保存した教訓の一覧と、削除・更新したメモリの一覧を報告してください


■ ⑥MCPの一斉修理

接続しているMCP（外部ツール連携）の総点検をお願いします。

やること:
1. 設定されているMCPサーバーを一覧化し、次の3分類に仕分けする
   - 正常: ツールを1回実際に呼んで成功を確認できたもの
   - 故障: エラーが出るもの（エラーメッセージを添える）
   - 休眠: 接続はできるが、直近1ヶ月使っていないもの
2. 「故障」はエラーログから原因を切り分ける（認証切れ／設定ミス／サービス側の障害／課金切れ）
3. 直せるものは修正手順を提示 → 私の承認後に修正 → 実際にツールを呼んで成功を確認
4. 「休眠」は削除候補として提示（判断は私がする）

守ること: 認証の再設定が必要な場合は、値を聞き出すのではなく「どこで何を発行すればいいか」の手順を示す

Fable×Sonnet分担ルール CLAUDE.mdスニペット集

CLAUDE.mdに貼るだけで効く運用ルール集。上位モデルの枠を「設計と検査」に温存し、実行部隊をSonnet 5に固定します。報告の信頼性・暴走防止のルールも同梱。

  • 分担ルール（model: sonnet固定）
  • 進捗報告の嘘を防ぐ一文
  • 過剰作業の抑制
  • 承認ゲート
  • 完了報告の型
  • メモリ運用ルール
■ 分担ルール（実行部隊はSonnet 5）

- サブエージェントを起動するとき → 必ず model: sonnet を指定する
- 実装・調査・単純タスクはSonnet側へ分担し、Fable 5は要件整理・全体設計・方針決定・品質レビューを担当する
- 設計と実装が密接に絡む難所だけは、Fable 5が直接対応してよい


■ 進捗報告の信頼性（嘘の報告を防ぐ）

- 進捗を報告する前に、各主張を実際のツール実行結果と突き合わせること
- 証拠を示せる作業だけを「完了」と報告する。未検証のものは「未検証」と明記する
- テストが失敗したら、失敗した事実と出力をそのまま報告する。スキップした工程は「スキップした」と言う


■ 過剰作業の抑制（頼んでいないことをさせない）

- 依頼された範囲を超えて、機能追加・リファクタ・抽象化をしない
- バグ修正に「ついでの掃除」は不要。将来の仮定のための設計もしない
- 起こり得ないケースのエラー処理・フォールバック・検証を追加しない


■ 承認ゲート（勝手に実行させない）

- 複数ステップの作業は、実行前にプランを提示して承認を待つ
- 削除・上書き・外部送信・公開・課金など取り消せない操作の前は、必ず確認を取る
- 既存の成果物を大幅に書き換える前は、何をどう変えるか予告してから着手する


■ 完了報告の型（読み手ファースト）

- 報告は結論から書く。1文目は「何が起きたか／何が分かったか」
- 編集・実装の完了時は「変えた箇所 / 触っていない箇所 / 確認してほしい箇所」を末尾に付ける
- 作業中の略語・矢印記法・自分で作ったラベルは、最終報告では使わない


■ メモリ運用ルール

- 私から同じ修正指示を2回以上受けたら、教訓としてメモリに記録する
- 教訓は1ファイル1件・冒頭に1行要約・理由つき。重複したら既存を更新する
- リポジトリや履歴を見れば分かることはメモリに書かない。間違っていたメモリは削除する

ループ設計テンプレート（記入例3本つき）

「ゴールと検証条件を渡して回しておく」ための設計シート。穴埋めするだけでループの設計図が完成します。量産系・定期系・見張り系の記入例つき。

  • 穴埋め式の設計シート
  • 設計チェック3点（数えられる成功条件 など）
  • 記入例: X投稿量産 / 朝のリサーチ便 / 問い合わせ見張り番
■ ループ設計シート（コピーして穴埋めしてください）

【型】        ターン型 / ゴール型(/goal) / 時間型(/loop・/schedule) / プロアクティブ型 のどれか1つ
【ゴール】     例: ○○が△△の状態になること（1文で）
【成功条件】   数えられる形で書く（例: テスト全部合格 / スコア90以上 / 下書き5本完成）
【検証方法】   成功条件をどう確かめるか（例: 実際に実行して結果を見る / チェックリストと突き合わせる）
【停止条件】   成功条件の達成 or 周回上限（例: 5周してダメなら止めて報告）
【担当】      設計・最終検査 = Fable 5（またはOpus） / 実行 = Sonnet 5
【失敗時】     何を残して止まるか（例: 詰まった箇所と原因の仮説をメモに書いて停止）

設計のチェック3点:
□ 成功条件は数えられるか（あいまいな「いい感じに」が残っていないか）
□ 作る人と検査する人を分けたか
□ 大きく回す前に、1周だけ試して消費量を見たか


■ 記入例1: X投稿の量産ループ（ゴール型）

【型】        ゴール型（/goal）
【ゴール】     今週ぶんのX投稿の下書きが揃っている状態
【成功条件】   下書き5本。各本文が140〜300字で、冒頭1行にフックがある
【検証方法】   各下書きをチェックリスト（文字数・フック・絵文字過多でない）と突き合わせる
【停止条件】   5本合格 or 8周で打ち切り
【担当】      構成と最終チェック = 上位モデル / 本文生成と修正 = Sonnet 5
【失敗時】     不合格の本文と落ちた理由を一覧にして停止


■ 記入例2: 朝のリサーチ便（時間型）

【型】        時間型（/schedule クラウド実行）
【ゴール】     毎朝、業界の新着情報が要約されて手元に届いている状態
【成功条件】   毎朝9時までに、新着5件以上の要約（各3行）が1つのメモにまとまっている
【検証方法】   要約に元リンクが揃っているか・重複がないかをセルフチェックしてから保存
【停止条件】   手動で止めるまで毎日実行
【担当】      初回の設計 = 上位モデル / 毎日の実行 = Sonnet 5
【失敗時】     取得に失敗したソース名を記録して、翌朝の周回で再試行


■ 記入例3: 問い合わせ・エラーの見張り番（プロアクティブ型）

【型】        プロアクティブ型（/schedule + /goal + Skill の組み合わせ）
【ゴール】     エラー報告・問い合わせが来たら、一次対応の下書きまで自動で終わっている状態
【成功条件】   新着1件につき「分類・原因の仮説・返信下書き」の3点セットができている
【検証方法】   別エージェントが3点セットの妥当性をチェックしてから私に通知
【停止条件】   ルーチン自体は手動停止まで。1件ごとの処理は3点セット完成で終了
【担当】      仕組みの設計 = 上位モデル / 見張りと下書き = Sonnet 5 / 送信の判断 = 人間（必ず）
【失敗時】     判断がつかない案件は「要人間判断」フォルダに退避して通知

第1部: ループ入門 — AIに「回る仕事」を渡す
────────────────────────

■ ループとは
「決めた停止条件に達するまで、AIが作業のサイクルを繰り返す」仕組みのこと。
1回の指示→1回の答え、で終わらせず、「できるまでやる」形で仕事を渡す。

■ ループは4種類。毎回どれか1つを選ぶ
① ターン型
  - 起動: あなたのプロンプト ／ 停止: タスク完了とAIが判断したとき
  - すべての基本。1回の依頼の中でも「調べる→作る→検証する」のサイクルが回っている
  - 強化のコツ: Skill（作業手順書）に検証ステップを書いておくと、毎回自動で自己チェックする

② ゴール型（/goal）
  - 起動: 成功条件つきの依頼 ／ 停止: 条件達成 or 試行回数の上限
  - 例:「トップページの品質スコアを90以上に。5回試してダメなら停止」
  - 評価役のモデルが毎周「条件を満たしたか」を判定し、ダメなら差し戻す

③ 時間型（/loop・/schedule）
  - 起動: 決めた時間間隔 ／ 停止: 仕事がなくなったとき or 手動停止
  - 例:「5分ごとにPR（作業の提出物）を確認して、指摘対応と修正をしておいて」
  - /loopは手元のPCで、/scheduleはクラウドで回る（PCを閉じても動く）

④ プロアクティブ型
  - 起動: イベントの検知（人の指示なし） ／ 停止: ルーチンは手動停止まで
  - 例: チャットの報告チャンネルを見張り、バグ報告が来たら分類→修正→別AIのレビューまで自動
  - 実体は「時間型＋ゴール型＋Skill」の組み合わせ技

■ ループ設計の原則
1. 停止条件は数えられる形で（テスト合格数・スコア・件数）。あいまいだと早止まり／回りすぎが起きる
2. 自己検証の手段を渡す（動かして確かめてから報告させる）
3. レビューは別エージェントに（作った本人のチェックは甘くなる）
4. 大きく回す前に小さく1周だけ試し、消費量を測る
5. 使用量（/usage）を見ながら運用する

第2部: AIエージェントを「チーム」で働かせる教訓
────────────────────────

AIを1体のアシスタントではなく、複数体のチームとして運用する時代の教訓集。

■ 教訓1: 公開の場で作業させる
エージェント同士のやりとりや作業ログは、個人DMではなく共有チャンネル的な場所に流す。
人間がいつでも途中経過を見られることが、暴走の早期発見と信頼につながる。

■ 教訓2: 役割をはっきり分ける
「何でも屋」を複数体置くと衝突する。実装係・調査係・レビュー係のように役割を切ると、
それぞれの精度が上がり、責任の所在も分かる。

■ 教訓3: 「北極星」を渡す
細かい指示より、「このチームは何のために動くのか」という目的を渡した方が、
判断に迷ったときに正しい方向へ倒れてくれる。

■ 教訓4: 信頼は段階的に広げる
最初から全権を渡さない。小さな仕事で実績を作らせ、確認の頻度を少しずつ減らしていく。
人間の新人と同じ育て方が、AIチームにも一番効く。

────────────────────────
第3部: CLAUDE.mdと「7つの指示方法」の使い分け
────────────────────────

AIへの指示の置き場所は7種類あり、それぞれ「読み込まれるタイミング」と「コスト」が違う。

① CLAUDE.md
  - セッション開始時に必ず読み込まれ、全体に効き続ける
  - 常時守ってほしい原則だけを書く。目安は200行未満。書きすぎると1つ1つが薄まる

② ルール（パス条件つきの指示）
  - 特定のフォルダ・ファイルを触るときだけ発動させられる
  - 「このフォルダでは○○する」を CLAUDE.md から分離して軽くする

③ Skill（作業手順書）
  - 呼び出したときだけ読み込まれる。手順が長い定型作業はここへ
  - 普段のコンテキストを圧迫しないのが最大の利点

④ サブエージェント
  - 別のコンテキストで隔離実行される。大量の読み込みが要る調査や、独立した検証に向く
  - 入れ子は深くしすぎない（数階層まで）

⑤ フック
  - 特定のイベントで必ず実行される決定的な自動化。「忘れずにやってほしいこと」はAIの記憶より確実
  - 例: 保存のたびに整形を走らせる、危険なコマンドをブロックする

⑥ 出力スタイル
  - 応答の形式そのものを変える、もっとも強い指示。文体・構成を常に固定したいときに

⑦ システムプロンプト追記
  - 起動時に外側から足す指示。ツール側の設定で全セッションに効かせたいものに

■ 使い分けの早見
- いつでも守ってほしい原則 → CLAUDE.md（短く）
- 特定の場所でだけ → ルール
- 長い手順の定型作業 → Skill
- 重い調査・独立した検証 → サブエージェント
- 絶対に忘れてはいけない処理 → フック
- 応答の型を固定 → 出力スタイル
